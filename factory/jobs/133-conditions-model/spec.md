## Problem & Goal
Consultants analyse variants (with and without an interface, a configuration) by copying the whole project today, and reviewers cannot see what was taken out or why (D27). A condition is the switch: a named, `present`-or-not element that assets, components, interfaces, threats, trees, steps, goals and claims may need. After this job `aegis-model` owns `Condition` with a stable `CF` visual ID, the sparse link side table and the eight III.6 ops; the store persists them additively; the diff and the client relation registry expose them. Business value (P7): one typed element and one side table back the applicability engine (134), the Configuration page (135) and the report (135) — no per-page switches, no copied projects. This slice deliberately stops before exclusions: no `Applicability`, no reasons, no lifted domain, no risk change, no page, no Slint (owner rule 2026-11-11).

## Acceptance Criteria
1. `aegis-model` exports `Condition`, `ConditionId`, `ConditionIdx`, `VisualPrefix::Condition` (`"CF"`), `MAX_CONDITIONS`, `MAX_CONDITIONS_PER_ELEMENT` and `Project::conditions()`. `VisualPrefix::Condition.format(0) == "CF00"` and `.format(100) == "CF100"`. Check: `cargo test --locked -p aegis-model --lib id`.
2. `Condition { name, description, present, provenance }` exposes `name()`, `description()`, `present()`, `provenance()`; `AddCondition` sets all four, description is plain text capped by `MAX_DESCRIPTION_CHARS` via `check_text`. Check: `cargo test --locked -p aegis-model --test conditions`.
3. The eight III.6 ops — `AddCondition`, `RenameCondition`, `SetConditionPresent`, `RemoveCondition`, `NeedCondition`, `UnneedCondition`, `NeedStepCondition`, `UnneedStepCondition` — each have an exact inverse documented in the `op.rs` table; applying each then its inverse restores the project **by `save()` bytes** (L06). Check: `cargo test --locked -p aegis-model --test conditions` and `cargo test --locked -p aegis-client --test undo_every_op`.
4. Guards, each with a test that only that guard refuses and that asserts the error variant (L09): duplicate/unknown condition id, blank/over-long name or description, a 257th condition, duplicate/unknown condition on a link, an unsupported `ElementRef` target, an over-long per-element condition list, unlinking a condition not listed, and removing a condition still linked (`ConditionInUse`). Error text uses public IDs and counts, never a name.
5. `condition_links` is a sparse `BTreeMap<ElementRef, SmallVec<[ConditionIdx; 2]>>` on `Project`; steps keep theirs in a new lazily allocated per-node slot of `TreeEntry::step_links` (no `ElementRef::Step`). Link lists are sorted and unique by `ConditionId`. Only Asset, Component, Interface, Threat, Tree, Goal and Claim are valid `ElementRef` targets in this job. Check: `cargo test --locked -p aegis-model --test conditions`.
6. `Project::eq`, `same_tree` and the relevant `diff_arena` closures compare condition references by **public ID**, not raw index (L06, L29). Check: `cargo test --locked -p aegis-model --test conditions` with a permutation of insertion order.
7. All eight new ops round-trip through `OpWire`/`OpView` encode/decode and `OpLogWriter`/`OpLogReader`, including the op-log byte cap and the metadata-op list. Check: `cargo test --locked -p aegis-model --test store`.
8. Snapshot: `conditions`, `condition_links` and per-step conditions serialize only when non-empty; a project with none saves the bytes it saves today and `tests/fixtures/project-v1.json` loads and re-saves byte-for-byte. Decode caps `Limit::Conditions` and `Limit::ConditionLinks` have just-under/just-over tests. A snapshot round trip carries links on **every** element kind (asset, component, interface, threat, tree, goal, claim and a step) and compares equal by `save()` bytes. Check: `cargo test --locked -p aegis-model --test store --test store_limits`.
9. `ProjectDiff::conditions()` lists added/removed/modified `ConditionId`s in canonical order and is counted by `is_empty()`; link and presence changes add no risk delta. Check: `cargo test --locked -p aegis-model --test conditions`.
10. The random op generator in `tests/common/mod.rs` covers all eight ops; `ops_properties` and `store_properties` still pass. Check: `cargo test --locked -p aegis-model --test ops_properties --test store_properties`.
11. `relations.rs` has one row per condition link kind (Asset, Component, Interface, Threat, Tree, Goal, Claim, Step → Condition), `many = true`, unique hyphenated Fluent labels in en/ja/pseudo, a `read` plus typed `link`/`unlink` returning the matching `Edit`; `ElementKind` gains `Condition` and `elements_of_kind` covers it. A test builds a project with one link of every kind and checks both directions. Check: `cargo test --locked -p aegis-client --test relations`.
12. `commands.rs` has typed `Edit`s whose `to_ops` yields exactly one `Op` each, plus a batch `Edit::RemoveCondition` that clears every link first in one undo step; `undo_label.rs` names them. Check: `cargo test --locked -p aegis-client --test undo_every_op` and `--test undo_labels`.
13. en, ja and pseudo catalogs resolve `condition`, `condition-present` and each `relation-*-condition` key; Fluent ids are hyphenated (L27). No `.slint` or `aegis-shell` file changes. `cargo fmt --all` and `scripts/ci.sh` pass with no new dependency. Check: `cargo test --locked -p aegis-client --test table_conventions` and `scripts/ci.sh`.

## Decisions
- **Description is a plain capped field on `Condition`.** `description: Arc<str>` checked with `check_text(text, MAX_DESCRIPTION_CHARS)`, set by `AddCondition` only; the III.6 op list has no `SetConditionDescription`, so the field is immutable until remove+re-add. Reason: keeps this slice to the exact op list and avoids adding `ElementRef::Condition` and description-map plumbing the backlog does not name (P3); the snapshot form remains additive.
- **New distinct caps:** `MAX_CONDITIONS = 256`, `MAX_CONDITIONS_PER_ELEMENT = 16`; `Limit::Conditions` and `Limit::ConditionLinks` are new variants/consts in `store/mod.rs`, not aliases of existing caps (L08).
- **Link storage:** `condition_links` is a sparse side table keyed by `ElementRef`; step conditions live in a new `condition: Vec<SmallVec<[ConditionIdx; 2]>>` slot in `TreeEntry::step_links`, alongside `via`/`attack_type`. Reason: the ADR 0010 and job 122 patterns — most elements need no condition and pay nothing.
- **Guard phasing:** `RemoveCondition` is unguarded in slice 133a (no links exist yet, mirroring 145a) and gains `ConditionInUse { condition, elements, steps }` in 133b together with the link ops. The client's `Edit::RemoveCondition` clears links first via `Edit::Batch` so removal is always one undo step.
- **Public IDs in comparisons:** link lists sort/dedupe by `ConditionId`; `eq`, `same_tree` and diff closures resolve indices through the condition arena (L06, L29).
- **Client scope is data only:** `Selection`/`ElementKind` gain `Condition` only to make the relation registry, edits and locales work; no page, picker UI or screenshot (owner rule 2026-11-11). No stored format outside the additive snapshot/op-log fields; no security, licensing, crypto, `unsafe`, dependency or user-data deletion. No open questions.
- **Slice 133a cap raised 2 lines** (600 -> 640 `max_lines`): the gate counted 602 lines, 2 over the cap; no code compression (L28 — do not add `rustfmt::skip` or distort code to meet a size cap).
