## Goal
A project can hold systems (Brake, ADAS, Gateway), and the user looks at one, a few or all of them (the "view"). After this slice the overview lists the five easiest attack paths among the threats of the view, and the five attack steps that lie on most of those easiest paths (choke points): the places where one control removes most of the attacker's best options. The model already has both algorithms per tree; this slice runs them over the view with bounded work, so the page stays fast on a large project.

Facts about what exists:
- Evaluation after controls, cached: `ws.cache().evaluate_residual_tree(project, tree_id) -> Result<&Evaluation<FeasibilityLevel>, ModelError>`. It fails for a tree that cannot be evaluated (an unrated step, an empty gate); skip such a tree.
- `Evaluation::root_value() -> &FeasibilityLevel`. `FeasibilityLevel` is `Ord`; greater means easier for the attacker.
- `Evaluation::attack_paths(&tree) -> Option<AttackPaths>`: an iterator of `AttackPath`, easiest first; the first path's feasibility equals the root value. `AttackPath::steps() -> &[NodeIdx]`, `feasibility() -> &FeasibilityLevel`, `bottleneck() -> NodeIdx`. `None` means the tree does not match the evaluation; skip it.
- `Evaluation::choke_points(&tree, k) -> Option<Vec<ChokePoint>>` over the tree's `k` easiest paths, already sorted by most paths, then most bottlenecks, then step order. `ChokePoint::step() -> NodeIdx`, `path_count()`, `bottleneck_count()`.
- Trees: `project.attack_tree(TreeIdx) -> Option<&AttackTree>`, `project.attack_tree_id(TreeIdx) -> Option<TreeId>`, `project.attack_tree_visual_id(TreeIdx) -> Option<String>`; `tree.root() -> NodeIdx`, `tree.get(NodeIdx) -> Option<&Node>`, `Node::label()`, `tree.id_of(NodeIdx) -> Option<NodeId>`.
- Threats: `project.threat_scenarios()` yields `(ThreatIdx, ThreatId, &ThreatScenario)`; `ThreatScenario::attack_tree() -> Option<TreeIdx>`.
- Systems: `project.system_use() -> SystemUse`, `SystemUse::threat(ThreatIdx) -> SystemSet`, `SystemUse::set_of(ids)`, `SystemSet::shows_in(view_set)`. Client `crate::systems::SystemView` (`is_all()`, `systems()`, `normalized(&Project)`).
- Step texts: `view::through_label(project, item) -> String` ("GW / OBD"), `project.step_via(TreeIdx, NodeIdx) -> Option<ItemRef>`, `view::step_other_system(project, &usage, tree, node) -> Option<String>` (the other system's name when the step leaves its tree's systems).
- Labels and tones: in `pages.rs` the private `feasibility_label(m, level) -> String`; `aegis_canvas::Tone::from_level(position, count)` with the position from `m.feasibility_levels().position(|(l, _, _)| l == level)`.
- `pages::overview_in(ws, view) -> Overview` builds the overview of a view; `pages::overview(ws)` calls it with all systems.

   ```rust
   /// How many trees are searched, how many paths each gives, and how many
   /// rows each list keeps.
   pub const TOP: usize = 5;

   /// One of the easiest attack paths of the view.
   #[derive(Clone, Debug, PartialEq, Eq)]
   pub struct PathRow {
       pub tree: TreeId,
       /// Short visual ID of the tree (`AT00`, ...).
       pub tree_visual_id: String,
       /// The tree's root label: what the attacker achieves.
       pub goal: String,
       /// The steps in path order: "Inject on CAN-1 via GW / OBD · Gateway",
       /// or the bare label for a step with no via.
       pub steps: Vec<String>,
       /// The path's feasibility after controls, as a label.
       pub feasibility: String,
       pub tone: Tone,
       /// The step that limits the path, to select it.
       pub bottleneck: NodeId,
   }

   /// A step that lies on many of the easiest paths of its tree.
   #[derive(Clone, Debug, PartialEq, Eq)]
   pub struct ChokeRow {
       pub tree: TreeId,
       pub tree_visual_id: String,
       pub goal: String,
       pub node: NodeId,
       /// The step's text, formed as in `PathRow::steps`.
       pub step: String,
       /// How many of the tree's searched paths hold the step.
       pub paths: usize,
       /// How many paths of the tree were searched (at most `TOP`).
       pub of: usize,
       /// On how many of them the step is the limiting one.
       pub bottlenecks: usize,
   }

   /// The easiest attack paths and the choke points of what `view` shows.
   #[derive(Clone, Debug, Default, PartialEq, Eq)]
   pub struct TopPaths {
       pub paths: Vec<PathRow>,
       pub choke_points: Vec<ChokeRow>,
   }

   #[must_use]
   pub fn top_paths(ws: &Workspace, view: &SystemView) -> TopPaths
   ```
   Give every public item and field a doc comment. Algorithm, in this order:
   1. Candidate trees: each tree linked by at least one threat that shows in the view (every threat when the view is all or the project has no systems), once each, in tree index order, with a residual evaluation that succeeds.
   2. Sort the candidates by root value, greatest first; the sort is stable, so ties keep tree index order. Keep the first `TOP`. (The `TOP` easiest paths of the view cannot lie in any other tree, because a tree's easiest path has its root value.)
   3. For each kept tree take the first `TOP` paths of `attack_paths`. Put all of them in one list, stable-sort by feasibility, greatest first, keep the first `TOP`: these are `paths`.
   4. For each kept tree call `choke_points(tree, TOP)`; `of` is the number of paths step 3 took from that tree. Put all in one list in tree order, stable-sort by `paths` descending then `bottlenecks` descending, keep the first `TOP`: these are `choke_points`.
   State the cost in the doc comment: O(threats + T log T) for T candidate trees to choose the trees, then `TOP` calls of `attack_paths` and of `choke_points`, each bounded by the tree size as documented in `eval.rs`.
