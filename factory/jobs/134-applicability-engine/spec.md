## Problem & Goal
Job 133 stored conditions and the links that say which elements need them, but switching a condition off changes nothing: every risk number still counts the steps and threats that do not exist in that variant. A consultant analysing "with and without the telematics unit" still has to copy the project, and a reviewer cannot see what was left out or why (D27, G50).

After this job, `aegis-model` derives which elements and attack tree nodes are excluded, with a reason list for each, and evaluates trees and risks without them: an OR gate ignores excluded alternatives, an AND or SEQ gate is excluded with any excluded child, and a threat whose tree root (or the threat itself) is excluded gets a "not applicable" risk instead of a level. The evaluation cache keeps all of this current when a condition is switched, within the 5 ms edit budget.

Business value (P7): one switch replaces a copied project per variant. The reasons are what a reviewer and an assessor ask for ("why is this threat not rated?"), and they are the data the Configuration page, the inspector banner and the report of job 135 show. Every moving part here is needed by that: the lifted domain makes OR/AND behave as an engineer expects, the reasons make the exclusion auditable, and the incremental cache keeps the switch instant on a large project.

## Acceptance Criteria
1. `aegis-model` exports `Lifted<V>` (`Value(V)`, `Excluded`) and `Applicable<D>` (an `AttributeDomain` with `Value = Lifted<D::Value>`): OR ignores `Excluded` children and gives `Excluded` only when every child is excluded; AND and SEQ give `Excluded` when any child is; otherwise the inner domain decides. The `*_kept` answers name the deciding child, so an OR gate never selects an excluded child. Check: `cargo test --locked -p aegis-model --test applicable_domain` (hand-built cases for each gate kind and a property test against a naive recursive evaluator written in the test).
2. `aegis-model` exports `Reason` (`#[non_exhaustive]`: `ConditionOff(ConditionId)`, `OwnerExcluded(ElementRef)`, `ViaExcluded(ItemRef)`, `AllPathsExcluded`) and `Applicability`, built by `Project::applicability()`. Direct reasons: an asset, component, interface, threat, tree, goal, claim or step that needs a condition whose `present()` is false gets `ConditionOff`. Propagation, in this order, adds `OwnerExcluded(owner)`: component -> child components (transitively), component -> its interfaces, component -> assets bound to it, asset -> threats on it, threat -> its tree (only when every live threat that uses the tree is excluded). A step whose via item (component or interface) is excluded gets `ViaExcluded(item)`. Goals and claims are excluded only by their own conditions. A gate (or root) is excluded when the `Applicable` rule says so and gets `AllPathsExcluded`; a tree whose root is excluded is itself excluded with `AllPathsExcluded`. Reason lists are sorted and unique. Check: `cargo test --locked -p aegis-model --test applicability` (one hand-built test per reason and per propagation edge, each gate kind, and a property test against an oracle written in the test from public getters only).
3. `Project::evaluate_tree`, `evaluate_threat`, `evaluate_risk` and the three residual variants evaluate with `Applicable<MaxMin<FeasibilityLevel>>`: excluded steps need no rating, excluded nodes have no value (`Evaluation::get` returns `None`), and attack paths, top-k paths and choke points never contain an excluded step. An excluded tree gives `Err(ModelError::TreeNotApplicable(TreeId))`; an excluded threat, or a threat whose tree is excluded, gives `Err(ModelError::ThreatNotApplicable(ThreatId))` from `evaluate_risk` and `evaluate_residual_risk`. Exclusion is checked before `NoAttackTree` and `MissingLeafValue`. A project where every condition is present computes exactly the numbers it computes today. Check: `cargo test --locked -p aegis-model --test applicability_eval` and `cargo test --locked -p aegis-model --test project --test eval --test explain`.
4. Sensitivity (`threat_sensitivity`, `residual_threat_sensitivity`) uses the same exclusions: an excluded step has no tipping point, and an excluded threat returns `ThreatNotApplicable`. Check: `cargo test --locked -p aegis-model --test applicability_eval`.
5. `ProjectEvalCache` holds the `Applicability` (`ProjectEvalCache::applicability() -> &Applicability`) and agrees with `Project` after every op and its inverse. Check: `cargo test --locked -p aegis-model --test ops_properties`.
6. Incremental invalidation: `SetConditionPresent`, `NeedCondition`, `UnneedCondition`, `NeedStepCondition` and `UnneedStepCondition` re-evaluate only the steps whose exclusion changed and their ancestors, and only the threats whose exclusion or tree root changed; a rating edit does not re-derive applicability. Every other op that can change applicability (component, interface, asset, threat, tree-structure and via edits, and removals) re-derives it too; a property test over the general op generator checks `cache.applicability() == project.applicability()` after every op. A test asserts with `recomputed_nodes()` that switching a condition linked to one step of one tree in a three-tree project leaves the other two trees untouched. Check: `cargo test --locked -p aegis-model --test applicability_cache`.
7. A shuffled-order property test applies a random set of switch ops (present toggles and need/unneed on steps and elements) in a random order through `apply_cached`, and after every op compares the cache with `ProjectEvalCache::new(&project)` (a full evaluation); two orders of the same present toggles end with equal caches. Check: `cargo test --locked -p aegis-model --test applicability_cache`.
8. A divan bench `benches/applicability.rs` at the large reference size (about 100,000 nodes: 25 trees of 4,000 nodes, one threat each, 64 conditions together linked to about 1% of the steps) measures `SetConditionPresent` through `apply_cached` and a rating edit while a condition is off; both medians are at most 5 ms on the reference machine, recorded in `build.md`. Check: `cargo bench --locked -p aegis-model --bench applicability`.
9. No change to the snapshot, op log or workspace formats, the client, `.slint` or `aegis-shell` files; no new dependency; `cargo fmt --all` and `scripts/ci.sh` pass. Check: `scripts/ci.sh`.

## Decisions
- **Not applicable is an error variant, not a new return type.** `ModelError::ThreatNotApplicable(ThreatId)` and `ModelError::TreeNotApplicable(TreeId)` sit beside `NoAttackTree` and `MissingLeafValue`, which already mean "no level can be given". Reason: the public return types (`Evaluation<FeasibilityLevel>`, `ThreatRisk`) stay, so the client, server and ~200 existing tests compile unchanged; `ModelError` is `#[non_exhaustive]`; the diff already maps an error to "no snapshot".
- **Excluded nodes have no value in the public `Evaluation<FeasibilityLevel>`.** The cache evaluates with `TreeEvalCache<Lifted<FeasibilityLevel>>` and keeps a projected `Evaluation<FeasibilityLevel>` (excluded slots `None`) synced on touched nodes, the same way threat risks are synced today. Reason: keeps every caller's types; `paths.rs` already skips OR children without a value.
- **Gate exclusion is structural.** Whether a gate is excluded depends only on which steps are excluded, not on ratings, so `Applicability` computes `AllPathsExcluded` by evaluating `Applicable<_>` over a unit domain, only for trees that have an excluded step. A tree whose structure cannot be evaluated (empty gate, cycle) gets no gate reasons; its evaluation error is reported as before.
- **A shared tree is excluded by its threats only when all of them are excluded.** Reason: another threat may still use it; that threat's risk must not vanish.
- **A threat is not excluded by its tree.** The threat stays in the lists; only its risk is not applicable (III.6 propagates threat -> tree, not back).
- **Reasons carry public IDs** (`ConditionId`, `ElementRef`, `ItemRef`), so two projects built in different orders give equal `Applicability` values (L29).
- **Fast path:** when every condition is present, `Project::applicability()` returns an empty value after scanning the conditions only, so projects without switches pay O(conditions).
- **Derivation is full, evaluation is incremental.** On a switch op the cache re-derives the whole `Applicability` (linear in links, owners and the nodes of trees with exclusions; no evaluation) and re-evaluates only the steps whose exclusion changed. Reason: P3; the derivation is cheap next to tree evaluation, and the bench proves the 5 ms budget. Architecture III.6's O(linked + propagated) applies to the evaluation work.
- **Excluded steps need no rating:** an unrated excluded step does not give `MissingLeafValue`. Reason: the engineer should not have to rate what does not exist in this variant.
- **`paths.rs` accepts an evaluation with value-less nodes off the live paths (134b rework).** `matches_tree` drops its per-node `eval.get(idx).is_none()` check and keeps the root-value, node-count and derivation checks. Reason: an excluded node has no value in the public view, so the old check made `attack_paths`, `top_k_paths`, `choke_points` and `top_k_hitting_set` return `None` for every tree with an exclusion; every node reached through AND/SAND from a valued node has a value, and OR already filters children without one, so the iterators never read an excluded node.
- **Uncached `Project::evaluate_*` derive applicability per call.** Reason: one implementation path; with the fast path and the linear derivation this keeps the diff budget at 100 changed threats.
