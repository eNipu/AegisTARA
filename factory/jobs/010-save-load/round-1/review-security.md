## Findings

1. `crates/aegis-model/src/store/wire.rs:245-275` (`KeyMap`), `:213-240` (`KeySet`), `:157,176` (`BoundedStr` allocates an `Arc<str>` for every key), together with `crates/aegis-model/src/store/snapshot.rs:262-266` (the whole snapshot is decoded before any key is resolved) — **hostile snapshots amplify memory about 11x, not the documented 3.65x.** Every 1-byte key costs one heap `Arc<str>` (about 32 B) plus a 16-24 B slot, while it takes only about 4 bytes of JSON (`"a",`), or 8 bytes for an impact pair (`"a":"x",`). Unknown keys are rejected only after the whole file has been decoded. I measured this on the branch. A 64 MiB snapshot of damage scenarios, each with 32 distinct one-character impact keys, reached a peak footprint of 792 MB. An asset-only version with 62 one-character property keys per asset reached 789 MB. Both then failed with `UnknownKey`. That is about 11-12x the file size. The spec says "each wire entity takes no more memory than its JSON text", and the ADR (`docs/adr/0009-save-load-format.md` ~l.290) states 3.65x. The `store_memory` gate (`benches/store_memory.rs:24-25`, `MAX_FACTOR = 5.0`) only covers the benign `typical` shape, so it cannot catch this. On a server, each concurrent hostile load can claim close to 0.8 GB (R3 says "protection against hostile files"). — **Fix:** resolve vocabulary keys to indices while decoding: give `KeySet`/`KeyMap`/`Key` fields a `DeserializeSeed` that holds `&Methodology`, so wire entities hold `Property`/`ImpactCategory`/`Level`/`ThreatCategory` indices and an unknown key fails at once. If that is too much for this job, at minimum: (a) add a hostile-shape case to `store_memory`, using short distinct keys at the property and impact caps, with its own gate; (b) state the measured worst-case factor in ADR 0009 next to the typical one; (c) correct the "no more memory than its JSON text" claim. Borrowing keys as `&'de str`/`Cow` alone still leaves about 6x, because of the `Vec<(Key, Key)>` slots.

## Checked, no issue

- **Q4 / R3 caps:** every string and list cap is enforced inside the visitor before the item is pushed (`BoundedVec`, `KeySet`, `KeyMap` check `len >= MAX` before inserting). The snapshot read is capped with `take(MAX + 1)` (`snapshot.rs:136-144`). The op-log line reader checks the cap before `extend_from_slice` (`op_log.rs:393`), so the line buffer never exceeds 64 KiB. serde_json's default recursion limit (128) is still on. Nothing calls `disable_recursion_limit`. Internally tagged `OpWire` buffering into `Content` is bounded by the 64 KiB line.
- **Typed faults:** the thread-local side channel is cleared before each decode and taken after it (`wire.rs:81-95`). No `untagged`/`flatten`/`alt` path swallows an error, so a stale fault cannot misreport.
- **Error contents:** `Decode` drops the serde_json message and keeps only line and column. The only decoded text in errors is a ≤64-byte key or scheme printed with `{:?}`, which escapes newlines and blocks log injection. This matches the spec, and AC14 covers it. The header `version` (≤256 B) is exposed only through `methodology_version()`, never in an error.
- **Q2/Q3:** no `unsafe` (`#![forbid(unsafe_code)]` is kept). The AC16 grep over `src/store/*.rs` prints nothing. The `expect`s in `fuzz/fuzz_targets/*` are test harness code, not library code.
- **Writer:** `within_caps`, the seen-bit check for repeated impact categories, and the record-size check keep the reused buffer bounded. Nothing is written on an encode error. `seq` overflow gives a typed error.
- **Reader sequencing:** a gap, a repeat or a step back gives `Sequence`. The iterator stops after the first error.
- **D7 (hash maps):** the new code has no hash maps. It uses sorted `Vec` with binary search.
- **D5 dependencies:** `serde` and `serde_json` are MIT/Apache-2.0, pinned through `Cargo.lock` (CI uses `--locked`), and needed. `libfuzzer-sys@0.4.13` gets NCSA through a per-crate exception only, not the global allow list. A `[bans] deny` with `wrappers = ["aegis-model-fuzz"]` keeps it out of shipped crates, and `scripts/deny.sh` now also checks `crates/*/fuzz/Cargo.toml`. The owner approved this in rework.md.
- **Secrets:** fixtures, fuzz seeds, benches and tests contain no secrets, tokens or customer data.

## Minor (not blocking)

- `snapshot.rs:136-139`: `read_to_end` grows the buffer by doubling, so a near-cap input can hold up to about 128 MiB of capacity for a 64 MiB file. If the loader is ever given a size hint, a bounded `Vec::with_capacity` would avoid this. Nothing to do now. Note it in the ADR's memory figures if finding 1 is addressed by documentation.
