Surface reviewed: library API and error messages only (the crate has no UI, CLI or server in this change). `PackError`, the 8 new `Limit` variants and their `Display` text, `MethodologyError::InvalidKey` / `UnknownViolatedProperty` key bounding, the `read_pack` / `write_pack` / `iso21434_r155` signatures and their doctests. No keyboard, context-menu, accessibility or UI-thread surface. All pack work is synchronous library code: `iso21434_r155()` is about 15 us, and a maximal pack reads in about 3.5 ms (build.md). Callers who load a user-supplied pack should still do it off the UI thread, and the ADR/docs could say so (see note 4).

Flow: the goal is met in one call, `Methodology::read_pack(reader)`. `iso21434_r155()` going from `MethodologyError` to `PackError` is a mechanical change (`From<MethodologyError>`), and the doctests were updated to match. `PackError::Methodology(#[from])` means `?` works the same for both. Fine.

Errors: each variant says what went wrong. `Decode` gives line and column, `UnsupportedFormat` reuses the store's text (including the newer-application hint), and `LimitExceeded` names the cap and its value and never quotes input. Quoting no input is a deliberate and correct choice. No silent failures were found.

Non-blocking suggestions (none block the merge; they can go into a later job, e.g. the admin UI / pack registry job where a person edits packs):

1. `crates/aegis-model/src/store/mod.rs` (`Display for Limit`, new arms) — a pack author who hits `label is longer than 1024 bytes` or `more than 16 levels in one impact category` is not told which entry, because `Limit` carries only `max`. The wording is accurate but the author must search a possibly 1.4 MB file. Fix (later): add an optional position to `PackError::LimitExceeded`, for example the line and column (the cap check runs inside the serde visitor, so `serde_json` can supply them), or the key of the enclosing entry. `Decode` already shows the position approach works. Do not add the offending text.
2. `crates/aegis-model/src/store/mod.rs` (`Limit::Properties` doc and Display) — the same variant now covers a pack's `violates` list, but its text says only "more than 64 properties". That reads correctly enough for the property list and is slightly ambiguous for `violates`. Optional: a separate wording, or a note in the `PackError` docs.
3. `crates/aegis-model/src/error.rs` (`PackError::Decode`) — "malformed methodology pack at line N, column M" gives no hint of the reason (missing field vs. unknown field vs. out-of-range number). Withholding the parser message avoids quoting input, which is justified. A short fixed category (an enum of reasons, without any input text) would help hand editors. Optional, later.
4. `crates/aegis-model/src/methodology/pack.rs` / docs — the cost notes give time and space, but do not say "do not call on the UI thread for user-chosen files". Worst-case time is a few ms, so it is inside the 50 ms budget on a normal machine, but a slow disk or network path in the reader is the caller's concern. One sentence in the `read_pack` docs would cover it.
5. `PackError::Io` — "I/O error: ..." has no hint what was being read. The caller knows the path, so this is fine for a library. A caller-facing example that adds the file name could go in the ADR or docs.

Positive: error key text is bounded to 64 bytes (ends in `...`, cut at a char boundary), so a message shown to a user can never be a megabyte. The shape of the `PackError` doctest (unsupported version, label cap) shows the intended handling.
