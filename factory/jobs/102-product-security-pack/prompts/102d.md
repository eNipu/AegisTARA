## Do
1. Create `docs/security-pack/en/06-security-questionnaire.md`, at most 220 lines, title `# 6. Security questionnaire answers`.
2. `## 6.1 How to use this chapter`: six to ten lines. The answers describe the product as shipped. The status words:
   - `Yes`: the product does it as built.
   - `No`: the product does not do it.
   - `Partly`: the answer explains the limit.
   - `Customer`: the customer does this in its own environment (the product is hosted by the customer).
   - `Planned`: decided but not built.
   - `Vendor`: a question about the vendor's organisation, not the product; the vendor answers it in the contract papers for each customer.
3. Sections `## 6.2` to `## 6.11`, each one table with the columns: ID, question, status, answer, reference. IDs run `Q-01`, `Q-02`, ... through the whole chapter without restarting. An answer is one to three sentences. A reference is a section number of this pack such as `2.2` or `4.5`, or `SECURITY.md`. At least 40 rows in total; aim for 45 to 55. The sections and the questions to cover:
   - `## 6.2 Hosting and architecture`: who hosts it; is it multi-tenant (single tenant, one deployment per company); does data leave our network; does the vendor have access to our data; is there telemetry; can it run air gapped; which third-party services it depends on at run time; where the data is stored.
   - `## 6.3 Access control`: single sign-on; MFA; password policy; brute force protection; session timeout; role-based access; least privilege per project; administrator separation; how a leaver is removed; shared or default accounts (the first administrator password is set by the customer and used only while no user exists; development login must be off).
   - `## 6.4 Cryptography`: encryption in transit; TLS versions; encryption at rest; password storage; key management; algorithms of our own; FIPS.
   - `## 6.5 Logging and monitoring`: are security events logged; what is in the log; can logs be changed; retention; SIEM export; clock.
   - `## 6.6 Secure development`: memory-safe language (Rust; state the rule on `unsafe` only as the standards file states it); code review; automated tests, property tests and fuzzing (only what the files show); static analysis (lints as errors); dependency checks (licenses, advisories, sources with `cargo-deny`); pinned toolchain and locked dependencies; a software bill of materials per release (CycloneDX).
   - `## 6.7 Vulnerability management`: how to report; response times (3 working days, 10 working days, 90 days at most); support period (five years from release, or the next major version plus one year, whichever is later); penetration test (answer `Vendor` unless a file in the repository records one; an internal security review exists in `docs/security-and-architecture-review.md`: you may say an internal review was done and its high and medium findings were closed only if `docs/adr/0054-security-hardening-sweep.md` and `docs/adr/0061-project-access-roles-and-membership.md` show that; otherwise leave it out); Cyber Resilience Act reporting.
   - `## 6.8 Updates and supply chain`: how updates are delivered; are they signed; can the app update itself silently (no: the user downloads and opens the installer); offline updates; how a customer verifies a bundle; license check without phone-home; signed installers (answer from the files: `docs/requirements.md` line 323 lists signed installers as NFR-06, jobs 099 and 100; if the code signing of installers is not built, the status is `Planned`).
   - `## 6.9 Privacy`: what personal data is stored; is personal data sent to the vendor or third parties; cross-border transfer; deletion of a user's data (with the limit from 5.3); data processing agreement (`Vendor`: needed only if support data is handed over).
   - `## 6.10 Availability and recovery`: backup (`Customer`: PostgreSQL backup; say what to back up: the database, the license file, the configuration); restore check (verify the history chain after a restore); high availability (one server instance per database; `Partly` or `No` as chapter 1.8 says); what happens if the license expires (grace period: confirm in `docs/adr/0032-license-tokens.md`); export of our data if we leave (project folder, reports, tables: confirm what exports exist in `docs/architecture.md` lines 1758-1765).
   - `## 6.11 Vendor organisation`: six to eight rows with the status `Vendor` and the same fixed answer, "Answered by the vendor in the contract papers for each customer; not a property of the product.": security certifications (ISO/IEC 27001, TISAX); information security policy; staff screening and training; access of vendor staff to customer data (here the answer may add: none through the product, see 1.6); subcontractors; incident notification to customers; insurance; business continuity of the vendor.
4. `## 6.12 Sources`: bullets `` - `path` `` for the five chapters and every other file an answer relies on.
5. Rules for the answers:
   - Never answer `Yes` where a chapter says `Customer`, `Planned` or names a limit. When in doubt between `Yes` and `Partly`, write `Partly` and state the limit.
   - No answer may contradict chapters 1 to 5. If you find that a chapter is wrong, do not fix it here: write it in build.md and end with `NEXT: planner`.
   - Follow the writing rules in `docs/security-pack/README.md`: plain words, no type names, no job numbers, no internal finding IDs; no certification, audit or organisational control claimed.
