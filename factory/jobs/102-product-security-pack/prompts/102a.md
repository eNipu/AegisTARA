## Do
1. Create `scripts/check-security-pack.sh` (POSIX `sh`, `set -eu`, executable, header comment with usage and the rules). Usage: `scripts/check-security-pack.sh [--complete] [PACK_DIR]`. `PACK_DIR` defaults to `docs/security-pack` under the repository root (find the root as `scripts/ci.sh` does: `$(cd "$(dirname "$0")/.." && pwd)`). Source paths are checked against the repository root, or against the directory in the environment variable `PACK_ROOT` when it is set (the test uses that). It prints one line per failure as `FAIL <file>: <reason>`, keeps going after a failure, and exits 1 if any rule failed, else prints `security pack ok (<n> files)` and exits 0. The rules:
   - **R1 names.** The only `.md` files allowed in `PACK_DIR/en` and `PACK_DIR/ja` are these six: `01-architecture-and-data-flow.md`, `02-cryptography.md`, `03-authentication-and-access.md`, `04-logging-and-retention.md`, `05-personal-data.md`, `06-security-questionnaire.md`. Any other `.md` file there fails.
   - **R2 pairs.** Every file in `ja/` must have the same file name in `en/`. With `--complete`, all six must exist in both `en/` and `ja/`. Without `--complete`, a missing chapter is not a failure (the pack is built slice by slice).
   - **R3 shape.** In each chapter file, line 1 starts with `# `. Take the chapter number `N` from the first two digits of the file name (`02` gives 2). Every line that starts with `## ` must start with `## N.M ` where `M` counts 1, 2, 3 with no gap and no repeat. There are at least two such headings. A line starting with `## ` inside a fenced code block is not expected; do not handle it.
   - **R4 sources.** The last `## ` section of each chapter must hold at least one line of the form `` - `path` `` (dash, space, backtick, path, backtick, nothing after). Every such path in that last section must exist (`[ -e "$root/$path" ]`).
   - **R5 parity.** For each chapter present in both languages: the list of heading numbers (`N.M`) must be equal, and the list of row IDs must be equal and in the same order. A row ID is the first cell of a table row when it matches two or more capital letters, a dash, and two or more digits (for example `| DF-01 |`, `| Q-12 |`): extract with a `sed`/`grep` pattern like `^| \([A-Z][A-Z]*-[0-9][0-9]*\) |`.
   - **R6 markers.** No file may contain the words `TODO`, `TBD`, `FIXME` or `XXX`.
   - **R7 translated.** A `ja/` file must not be byte-identical to its `en/` file (`cmp -s`).
   - **R8 length.** No chapter file is longer than 220 lines.
2. Create `scripts/check-security-pack-test.sh` (POSIX `sh`, `set -eu`, executable). It makes a temporary folder (`mktemp -d`, removed by a `trap`), writes a tiny good pack there (two chapters, `01-...` and `02-...`, in `en/` and `ja/`, each with two numbered sections, one table row with an ID, and a sources section naming a file the test also creates under the temporary `PACK_ROOT`), and runs the script on it. It asserts exit 0 for the good pack, then for each case below copies the good pack, breaks one thing, and asserts exit 1 and that the output contains `FAIL`:
   a Japanese chapter with one section removed; a Japanese chapter with its row ID removed; a source path that does not exist; a heading numbered `1.3` after `1.1`; an extra file `en/07-extra.md`; a line containing `TODO`; a `ja/` file copied from `en/`; and, with `--complete`, the good two-chapter pack (four chapters are missing). It prints `ok  <case>` or `FAIL <case>` per case and exits 1 if any case did not behave as expected, else prints `all cases passed`.
3. Create `docs/security-pack/README.md` (about 40 lines): what the pack is and who it is for; the list of the six chapters with links to `en/` (the `ja/` column says "added in a later change" for now, as plain words, not as a marker word from R6); the three writing rules below; how to check it (`sh scripts/check-security-pack.sh`); that the pack describes the product and is re-read for every release.
4. Create `docs/security-pack/en/01-architecture-and-data-flow.md`, at most 180 lines, title `# 1. Architecture and data flow`, with these sections in this order:
   - `## 1.1 Summary`: five to eight plain sentences. The customer hosts the server in its own cloud or data center; the vendor hosts nothing and receives no data; the desktop app is native; a standalone mode runs with no server.
   - `## 1.2 Deployment modes`: a table of the modes that exist in the code: server mode (desktop app, `aegis-server` container, PostgreSQL, the customer's TLS proxy, optionally the customer's identity provider) and standalone mode (one desktop process, embedded server on `127.0.0.1` with a random port, a project folder on disk, no login). For each: what runs where, who operates it.
   - `## 1.3 Components`: a Mermaid `flowchart` adapted from `docs/architecture.md` lines 1213-1238 using product words a buyer understands (no type names), then a table: component, role, runs as (the container runs as a non-root user: `docs/architecture.md` line 1856).
   - `## 1.4 Data flows`: a table with IDs `DF-01`, `DF-02`, ... and columns: ID, from, to, what is sent, protocol and protection, who starts it. Cover: app to server (gRPC over HTTP/2 or gRPC-Web over HTTP/1.1, inside HTTPS that ends at the customer's proxy); server to PostgreSQL (plain TCP on a private network by default, or TLS with `AEGIS_DB_TLS`); app to the identity provider at company login (OIDC, system browser); server to the identity provider (fetching signing keys to validate tokens: confirm in `crates/aegis-auth/src/jwks.rs` before you state it); app to the update address (only when `update_url` is set; fetches a signed manifest and, when the user asks, the installer); standalone app to its embedded server (loopback only); files the user exports (reports, tables) written to a local folder. State for each whether it leaves the customer's network.
   - `## 1.5 Trust boundaries`: the boundaries and what is checked at each: the network edge (customer's TLS proxy), the server's login layer (every call except the public account calls and `GET /healthz` needs a valid login), the per-project permission check, the database network, the desktop operating system account. State the standalone trade-off plainly: any process of the same operating system user on the same machine that finds the loopback port can act as the user; it is not reachable from the network.
   - `## 1.6 What leaves the customer's network`: by default nothing. No telemetry, no license server, no vendor-hosted service (the license is a signed file checked offline). The only optional outbound flow is the update check, which an air gapped site leaves off. Before you write "no telemetry", confirm it: run `grep -rn -i 'telemetry\|analytics\|sentry' crates/*/src crates/*/Cargo.toml Cargo.toml` and record the result in build.md. Cloud AI providers are `Planned` and opt-in (`docs/requirements.md` line 315, NFR-01).
   - `## 1.7 Where data is stored`: a table: PostgreSQL (projects, operation history, baselines, figures, users, sessions, settings, event log), the standalone project folder (`ops.jsonl`, `ops.meta`, `snapshots/`, `manifest.json`), the desktop settings file (list the fields from `settings.rs`; it never holds a password or token), the operating system keychain (the session token, only when the user ticks "keep me logged in"), the export folder. Say for each who controls it. Do not claim a local project cache on the laptop unless you find it in `crates/aegis-client/src`; `docs/direction-v1.md` describes one as a plan.
   - `## 1.8 Limits to know`: one server instance per database (`docs/deployment.md` lines 86-87); TLS for clients is the customer's proxy, not the server; the product does not encrypt data at rest itself (disk or database encryption is the customer's); password login has no e-mail reset and no MFA.
   - `## 1.9 Sources`: bullets `` - `path` `` for every file the chapter relies on, repository-relative, nothing after the closing backtick.
